# Принятые решения и допущения

Формат: дата · вопрос · решение · почему.

## Этап 0 — каркас

**2026-10-14 · Входные файлы `docs/input/`**
В выданном окружении не было `TOP.xlsx` и образца этикетки по указанным именам; в соседнем
репозитории владельца (`errxr3/Sklad`) лежали `docs/spravochnik-artikulov.xlsx` и
`docs/obrazec-etiketki.pdf`. Структура xlsx совпадает с описанной в SPEC §9 (листы «Полотна»,
«Алюминий», «Безрамные», заголовки в строке 2, артикулы с 3-й строки, подписи подгрупп в столбце B)
и даёт ровно 306 строк — то самое число, что в SPEC §6.9 («Скопировано 306 строк»). Поэтому файлы
скопированы в `docs/input/` как `TOP.xlsx` и `Пример_этикеток.pdf` и считаются входными данными.
Скриншотов гугл-таблицы (`gsheet_*.png`) не было — экран «Остатки» делается по текстовому описанию
SPEC §6.9, которое задаёт состав строк, столбцы, цвета и порядок однозначно.

**2026-10-14 · SQLAlchemy синхронный, драйвер psycopg 3**
Выбран синхронный SQLAlchemy 2.x: нужны понятные транзакции и `SELECT ... FOR UPDATE` на каждом
скане, а нагрузка (2–4 человека на площадку) ничтожна. Асинхронность добавила бы сложности без выгоды.

**2026-10-14 · Строки-заголовки подгрупп хранятся в `articles`**
Экран «Остатки» (SPEC §6.9) должен выводить строки ровно в порядке TOP.xlsx, включая строки-заголовки
(«ПОЛОТНА», «БЕЗРАМНЫЕ КРУГЛЫЕ»). Чтобы порядок был одним полем сортировки, заголовки хранятся в той
же таблице `articles` с `kind='header'` и `name_norm = NULL`; ограничение БД следит, чтобы у артикулов
`name_norm` был заполнен, а у заголовков — пуст. Заголовки нельзя выбрать при печати и к ним нельзя
привязать зеркало (внешний ключ ведёт на артикул, а в формах выбора фильтр `kind='article'`).

**2026-10-14 · Статусы, роли и типы движений — VARCHAR + CHECK, а не PostgreSQL ENUM**
Значения заданы кортежами в `app/statuses.py` и проверяются ограничением CHECK. Это избавляет от
болезненных миграций типа ENUM при добавлении, например, нового типа движения.

**2026-10-14 · Дополнительные поля и таблицы к SPEC §8**
- `sites.sort_order` — порядок столбцов площадок на экране «Остатки» задаёт админ (SPEC §6.9).
- `articles.kind`, `articles.color_hex` — строки-заголовки и цвет подгруппы из заливки TOP.
- `units.accepted_at` — время приёмки, чтобы отказ «Уже на складе (принято 10.10 в 14:20)» не искал
  запись в журнале на каждый скан (SPEC §11 требует один запрос на скан).
- `users.is_service` — служебный сборщик «Остаток на запуск» (SPEC §6.11): виден в списках сборщиков,
  но не может войти в систему.
- `api_keys` — ключи API для BLAGO OTGRUZKI (SPEC §10), хранится только хеш.
- `inventories.article_ids` (JSONB) — инвентаризация группы артикулов вместо всей площадки (SPEC §6.6).
- `mp_shipments.article_name` — исходное написание артикула из BLAGO OTGRUZKI, для текста отказа.
- Частичный уникальный индекс `uq_tasks_article_per_day` — одна задача на (дата, сотрудник, артикул),
  чтобы начальник смены не плодил дубли одной задачи.

**2026-10-14 · Неизменяемость журнала**
Триггеры `movements_no_update`, `movements_no_delete`, `movements_no_truncate` на `movements`
возбуждают исключение. Тесты чистят таблицу между собой, временно отключая триггеры
(`ALTER TABLE ... DISABLE TRIGGER USER`) — это делает только тестовая фикстура, в приложении
отключения нет.

**2026-10-14 · Python 3.13 локально, 3.12 в образе**
В образе зафиксирован `python:3.12-slim` как требует SPEC §2. В выданном окружении установлен
Python 3.13 — тесты гонялись на нём; код не использует ничего, что различается между 3.12 и 3.13.

**2026-10-14 · Тестовая база**
Тесты требуют настоящий PostgreSQL. Строка подключения — `TEST_DATABASE_URL`, иначе имя базы из
`DATABASE_URL` с суффиксом `_test`. Фикстура пересоздаёт схему и применяет миграции `alembic upgrade head`,
то есть тесты проверяют и миграции.

## Этап 1 — справочник, сотрудники, вход, роли

**2026-10-14 · Проверка ролей — в классе маршрута, таблица в одном месте**
`app/roles.py` держит таблицу `(метод, путь) → роли`. Класс `GuardedRoute` (app/web.py) до вызова
обработчика проверяет вход, роль, при необходимости открытую смену и CSRF. Маршрут, которого нет в
таблице, закрыт для всех — «по умолчанию запрещено». Тесты проверяют и обратное: в таблице нет строк
без маршрутов. Так скрытая кнопка никогда не остаётся единственной защитой.

**2026-10-14 · CSRF проверяется централизованно**
Токен лежит в подписанной cookie-сессии, приходит полем `csrf_token` формы, заголовком `X-CSRF-Token`
или полем JSON. Проверка — в `GuardedRoute`, поэтому её нельзя забыть в новом обработчике.
Сравнение токенов — побайтово (`hmac.compare_digest` не работает со строками вне ASCII).

**2026-10-14 · Цвета темы из TOP.xlsx**
В файле часть строк залита цветом темы, а не явным RGB. Цвет темы разворачивается по `xl/theme/theme1.xml`
с учётом оттенка (tint), затем заменяется ближайшим цветом палитры по умолчанию из SPEC §6.9. На
приложенном файле это даёт ожидаемое: полотна — #FFE0C1, алюминий — #DCE0F8, алюминий на ноге — #FFE5E5,
Ambient 4000 — #B7E1CD, gorizont/vert — #DEEFA0. Админ может поменять цвет подгруппы вручную.

**2026-10-14 · Служебный сборщик не может войти**
У сотрудника «Остаток на запуск» (SPEC §6.11) в поле `pin_hash` заведомо невалидное значение, он
помечен `is_service` и не показывается на экране входа — но доступен в списках выбора сборщика.

**2026-10-14 · Сообщения после POST передаются через адрес**
После POST делается редирект на страницу со `?ok=` или `?err=` (urlencode). Так обновление страницы
не повторяет действие, а сообщение видно пользователю.

## Этап 2 — зеркала: статусы, печать, приёмка

**2026-10-14 · Тип движения «print» и «assembler_change»**
SPEC §8 требует, чтобы статус менялся только вместе с записью в `movements`. Чтобы по журналу
можно было восстановить состояние любого зеркала (тест §12 п. 5), создание зеркала тоже пишет
движение — тип `print` (из «ничего» в «Напечатано»). Смена сборщика пишет движение `assembler_change`
без изменения статуса. Оба типа добавлены в список допустимых значений `movements.type`.

**2026-10-14 · Блокировка строки — `FOR UPDATE OF units`**
У модели `Unit` связанные таблицы подтягиваются внешним соединением, а PostgreSQL отказывается
применять `FOR UPDATE` к nullable-стороне outer join. Поэтому блокируется именно строка `units`
(`with_for_update(of=Unit)`): это и есть нужная гарантия «два скана — один успех».

**2026-10-14 · Печать требует открытой смены**
SPEC §4 запрещает сборщику и грузчику сканирующие операции без смены, а SPEC §6.3 говорит, что
площадка зеркала — это площадка текущей смены. Поэтому печать этикеток (`POST /make/print`) тоже
внесена в список маршрутов, требующих открытой смены. Начальник смены и админ работают без неё:
площадка берётся из их площадки по умолчанию, иначе первая активная.

**2026-10-14 · Перенос названия артикула на этикетке**
Название переносится по словам и уменьшается, пока не влезет целиком в две строки; слово рвётся по
буквам только если даже минимальный шрифт не помогает. Текст никогда не обрезается — обрезанный
артикул на складе хуже мелкого.

**2026-10-14 · Property-based тест остатка**
Полный прогон hypothesis против настоящей базы медленный, поэтому сделано два теста: один
детерминированный на 1000 случайных операций с фиксированным зерном (как просит SPEC §12 п. 5)
и один hypothesis-тест на коротких последовательностях (8 примеров), который ищет неожиданные
сочетания операций. Оба сравнивают остаток по `units` с остатком, восстановленным по `movements`.

## Этап 3 — смены по QR и задачи

**2026-10-14 · Статичный QR можно сфотографировать**
Как и предупреждает SPEC §5.3, лист с кодом смены можно сфотографировать и уносить с собой.
Поэтому: код хранится только хешем, перевыпуск ломает старый лист одним нажатием, в смене
сохраняются IP и User-Agent устройства, а при необходимости включается проверка геолокации
(координаты площадки и радиус, по умолчанию 300 м). Это компромисс между защитой и тем, что
у сотрудников обычные телефоны без специальных меток.

**2026-10-14 · Окончание смены — тоже по скану кода**
Чтобы нельзя было «добавить часы» из дома. Если сотрудник ушёл, не закрыв смену, в 00:05 по Москве
она закрывается автоматически с временем последнего скана в эту смену (или временем начала, если
сканов не было), а начальник смены может поправить время с обязательным комментарием — прежние
значения сохраняются в `edit_note`.

**2026-10-14 · «Сделано» в задачах считается по журналу, а не хранится**
Факт по задаче — это число зеркал этого сборщика и артикула, принятых сегодня по Москве, минус
списанные в тот же день. Ничего не хранится и не вводится руками, поэтому цифра всегда совпадает
с журналом. Проверено тестом на границе суток 23:59/00:01 по Москве.

**2026-10-14 · Планировщик внутри приложения**
APScheduler запускается вместе с приложением (можно выключить переменной SCHEDULER_ENABLED=0,
что и делают тесты). При нескольких копиях приложения автозакрытие выполнится несколько раз, но
повторный проход ничего не портит: закрываются только смены без `ended_at`.

## Этап 4 — отгрузка и складские операции

**2026-10-14 · Обязательный второй скан держит зеркало на складе**
SPEC §12 п. 7 требует, чтобы при несовпадении артикула с заказом зеркало осталось на складе.
Поэтому при включённом обязательном скане ШК маркетплейса первый скан этикетки зеркало не отгружает:
сервер проверяет статус и площадку и отвечает «Отсканируйте ШК маркетплейса», а отгрузка происходит
одной транзакцией после второго скана — когда сверка пройдена. Номер зеркала, ожидающего второй скан,
держит страница в браузере, на сервере состояние не копится.

**2026-10-14 · Отправка на другую площадку не меняет площадку зеркала**
При отправке зеркало получает статус «В пути» и остаётся числиться за площадкой-отправителем, а
площадка назначения пишется в журнал (`journal_to_site_id`). Приёмка на площадке-получателе сверяет
её с последней отправкой: «Зеркало отправлено на Учительскую» — понятный отказ вместо тихой ошибки.

**2026-10-14 · Что исключается из расхождений инвентаризации**
Любое зеркало, по которому было движение после старта инвентаризации, не попадает ни в «не
отсканировано», ни в «лишнее» (SPEC §6.6). Так пересчёт не ломается от того, что в это же время
грузчик отгружает паллету.

**2026-10-14 · Номер паллеты берётся из базы, а не из кеша связи**
После смены `pallet_id` в той же сессии связанный объект ещё хранит прежнее значение, поэтому
в текстах отказов паллета читается напрямую по идентификатору — иначе в сообщении «Уже отгружено»
вместо номера появлялся прочерк.

## Этап 5 — остатки как в гугл-таблице

**2026-10-14 · Скриншотов гугл-таблицы не было**
Файлов `gsheet_*.png` во входных данных нет, поэтому экран собран строго по тексту SPEC §6.9:
порядок строк из TOP.xlsx (включая строки-заголовки подгрупп), исходное написание артикула,
столбцы «Учительская», «Коминтерна», «Задачи на …», розово-красный фон нулевых остатков,
цвета строк из заливки TOP, закреплённые шапка и первый столбец, компактная плотность.

**2026-10-14 · Падеж в заголовке столбца задач**
В таблице столбцы называются «Задачи на Учительской» и «Задачи на Коминтерна». Автоматически
склонять произвольные названия невозможно, поэтому есть простое правило: окончание «-ская»
переходит в «-ской», остальные названия остаются как есть. Для двух рабочих площадок это даёт
ровно то, что в таблице.

**2026-10-14 · Данные на экране не обновляются сами**
Страница показывает остатки на момент загрузки, рядом — время и кнопка «Обновить» (SPEC §6.9):
иначе цифры поедут под рукой во время копирования столбца.

**2026-10-14 · Лист «Остатки из системы» начинается со строки заголовков**
В A1..E1 пишутся названия столбцов, данные идут с 2-й строки, в G1 — «Обновлено: …». Формулы
ВПР из README ищут по имени артикула и от этого не зависят. Лист перезаписывается одним
`batch_update`, чтобы он не оказался наполовину пустым во время обновления.

**2026-10-14 · Миграция 0003**
Типы движений `print` и `assembler_change` появились на этапе 2, когда миграция 0001 уже была
применена на моей базе разработки. Чтобы любая база пришла к одному состоянию, добавлена
миграция 0003, которая пересоздаёт ограничение `ck_movements_type` с полным списком.

## Запуск и образ

**2026-10-14 · В образе приложения нет системных пакетов**
Сначала в `Dockerfile` ставились `postgresql-client` и `curl`. Клиент postgres в образе приложения
не нужен (бэкапы снимает контейнер postgres), а проверка живости делается самим Python — поэтому
слой `apt-get` убран: сборка быстрее, образ меньше и не зависит от доступности зеркал Debian.

**2026-10-14 · Частая проверка живости в Caddy**
По умолчанию Caddy перепроверяет upstream раз в 30 секунд, и сразу после `docker compose up`
сайт успевал отдать 503 уже работающему приложению. Сначала стояли `health_interval 3s` и
`health_timeout 2s`; 15.10 таймаут поднят до 15 секунд, а интервал — до 5: на медленных машинах
(Docker Desktop под Windows) двух секунд может не хватить, и Caddy считал бы живое приложение мёртвым.

**2026-10-14 · Запуск на Windows одним файлом**
Владелец работает в Windows-консоли, где нет `cp` и прочего. Добавлены `start.bat` (проверяет
Docker Desktop, создаёт `.env` со случайным ключом подписи сессий, поднимает контейнеры, ждёт
ответа приложения, при первом запуске создаёт администратора и импортирует справочник, открывает
браузер) и `stop.bat`. Файл `.gitattributes` следит, чтобы bat-файлы выгружались с переводами
строк CRLF.

## Этап 6 — интеграция и сдача

**2026-10-15 · Переводы строк в скриптах на Windows**
У владельца приложение не стартовало: `exec /app/scripts/entrypoint.sh: no such file or directory`.
Git на Windows выдал `.sh` с переводами строк CRLF, а Linux не исполняет скрипт с `\r` в первой
строке. `.gitattributes` (`*.sh eol=lf`) защищает только новые выгрузки, поэтому дополнительно:
при сборке образа `\r` вычищается из `scripts/*.sh`, а контейнер бэкапа очищает смонтированный
`backup.sh` перед запуском. Теперь запуск не зависит от настроек git.

**2026-10-15 · Геопозиция запрашивается только при включённой геопроверке**
Сквозной тест показал: экран начала смены всегда запрашивал геопозицию, и пока человек не ответил
на запрос разрешения браузера, смена не начиналась (таймаут геолокации не идёт, пока висит запрос).
Теперь геопозиция спрашивается только если хотя бы у одной площадки включена проверка, и есть свой
страховочный таймер на 8 секунд.

**2026-10-15 · Ключ API показывается один раз**
В базе хранится только SHA-256 ключа. Ключ выводится на экран сразу после создания и больше нигде
не появляется — потерянный ключ отключают и создают новый.

**2026-10-15 · Документация API — свой Swagger UI**
FastAPI по умолчанию грузит Swagger UI с CDN и открывает `/docs` всем. Встроенные `/docs` и
`/openapi.json` выключены, вместо них свои маршруты, закрытые для всех, кроме администратора
(SPEC §10), а сам Swagger UI лежит в `static/vendor/`.

**2026-10-15 · Сквозной тест браузером**
Тест поднимает настоящий сервер приложения на свободном порту против тестовой базы и проходит
сценарий SPEC §12 в Chromium через Playwright. Камера подменяется вызовом того же обработчика,
который вызывает камера (`window.Sklad.shiftCode`), печать — тем же POST, что и кнопка «Печать»
(PDF уходит в новую вкладку), номер этикетки тест берёт из базы — как сканер считал бы его с
наклейки. Если Chromium в окружении нет, Playwright сообщит об этом при запуске.

## 2026-10-20 — Камера: zxing-wasm вместо html5-qrcode

**Вопрос.** На телефоне камера включалась, но этикетка 58×40 не читалась.
**Причина.** html5-qrcode перед распознаванием ужимает кадр до размера окошка на экране
(~340 px): тонкие полосы Code 128 сливаются. Проверено подставной камерой в Chromium:
этикетка на половину кадра 1280×720 не читалась ни разу за 150 попыток.
**Решение.** Свой цикл в `static/scan.js`: кадр с камеры (до 1920×1080) берётся в полном
разрешении, распознаётся средняя полоса (она же рамка-прицел на экране). Где есть
`BarcodeDetector` с Code 128 (Android Chrome) — он, иначе zxing-wasm 3.1.4 (ZXing C++,
MIT/Apache-2.0), файлы в `static/vendor/`, wasm отдаётся с нашего сервера. Форматы — только
Code 128 и QR. Этикетка читается даже на 1/5 ширины кадра. К ссылкам на статику добавлена
метка версии (`?v=` — хэш файлов), чтобы телефоны не держали старый скрипт после выкладки.
Тест: `tests/test_e2e_browser.py::test_camera_reads_printed_label` (видео Y4M из настоящей
этикетки PDF подаётся как камера).

## 2026-10-20 — Кладовщик печатает этикетки по задачам, сборщик только сканирует

**Запрос владельца.** Начальник смены ставит задачи каждому сборщику; утром выдаются
комплектующие со штрихкодами. Сборщику оставить только скан зеркала. Нужен аккаунт
кладовщицы, которая по поставленным задачам заранее печатает этикетки; несделанное —
убирать «висящие» напечатанные этикетки из скана.
**Решение.**
- Новая роль `storekeeper` («Кладовщик», миграция 0005 — ограничение `ck_users_role`).
- `units.task_id` (FK на задачу, `ON DELETE SET NULL`): этикетка помнит задачу, под которую
  напечатана. «Напечатано» по задаче = этикетки задачи, кроме аннулированных (списаны, ни разу
  не побывав на складе); «висит» = в статусе «Напечатано»; «сделано» — прежний подсчёт по приёмкам.
- Страница `/labels` «Печать по задачам» (кладовщик, начальник смены, админ): печать на
  недостающее до плана количество — на день, на сборщика, на задачу (с явным количеством —
  «Допечатать»). Повторная печать на день ничего лишнего не печатает.
- «Убрать висящие» (задача / сборщик / день) и «Убрать» по одной этикетке в списке
  «Напечатано больше суток»: существующий переход «Напечатано» → «Списано» движением
  `label_void` с пометкой «этикетка не использована». Скан убранной этикетки — красный экран.
  Почему не удалять: номера и журнал движений неизменяемы (SPEC §8), а аннулирование видно
  в журнале. Задача, перенесённая на завтра копированием, получает новые этикетки.
- Сборщик: меню только «Мой день» (смена, скан, задачи; прогресс обновляется после скана).
  `/make`, `/make/print`, `/stock`, `/mirror` для сборщика закрыты на сервере; приёмка сканом
  своих зеркал — как раньше, со сменой. Тесты, где сборщик печатал сам, переписаны под новый
  порядок (это изменение требований владельцем, SPEC §4 обновлён).

## 2026-10-20 (2) — Состав ролей, погрузка по каналам, возвраты, BLAGO

**Запрос владельца** (дословно по пунктам): у начальника смены оставить табло, печать по
задачам, остатки, поиск зеркала, «в пути»/«напечатано» больше суток, журнал, табель, план/факт,
«Сделал зеркало» убрать совсем; кладовщице — только печать по задачам своего производства,
без «Печать всего на день» и «Допечатать»; сборщику — только сканер; грузчику убрать задачи,
погрузка по каналам (Ozon, WB, СГТ, КГТ, СДЭК) с описанием при закрытии (Ozon — машины
Озон1…Озон3) и перемещение между производствами; новая роль «Возвраты» (приёмка на
Коминтерна, печать ШК для зеркал без маркировки); надпись BLAGO, новый вид; выдерживать много
пользователей одновременно.
**Решения.**
- Доступ — заново в `app/roles.py` (таблица остаётся единственным источником правды, тест
  ролей параметризован по ней). Ссылки в шаблонах показываются через `can(path)` из той же
  таблицы. Админ сохраняет всё, включая убранные у начальника операции (инвентаризация,
  списание, отмена отгрузки, «Выработка», «Состояние»), — иначе этими функциями некому было бы
  пользоваться.
- «Сделал зеркало» удалён (маршруты `/make`, `/make/print`). Перепечатка той же этикетки —
  в карточке зеркала у начальника смены.
- Задачи ставятся только сборщикам (не служебным): грузчик работает по каналам без задач.
- Погрузка: модель `pallets` сохранена как «отгрузка канала» (номер P+дата), добавлено
  `pallets.note` (миграция 0006). Ozon закрывается только с машиной из `OZON_TRUCKS`.
- Перемещение: грузчик отправляет и принимает; оба скана требуют открытой смены (площадка
  берётся из смены).
- Возвраты: площадка — «Коминтерна» (`RETURNS_SITE_NAME`). Печать ШК без маркировки создаёт
  зеркала «Напечатано» и тем же действием принимает их на склад (движения print + accept с
  пометкой «возврат без маркировки»), «сборщик» — служебный «Возврат без ШК» (миграция 0006).
- Бренд: шапка, вход, заголовки и этикетка — «BLAGO» вместо «СКЛАД» (на этикетке тоже, чтобы
  сотрудники видели одно название). Старые напечатанные этикетки сканируются как раньше —
  проверяется номер, а не надпись.
- Нагрузка: пул БД 10+20 соединений уже был; добавлено долгое кэширование `/static/*` в Caddy
  (адреса статики с меткой версии `?v=`, включая wasm камеры), чтобы телефоны не качали
  скрипты и библиотеку камеры при каждом открытии.

## 2026-10-21 (3) — Любой прошедший день отгрузки — по журналу движений

Владелец хочет открывать любой отгрузочный день с отгрузками и остатками того дня. Отдельные
«снимки дня» не заводились: журнал движений неизменяем (триггер запрещает UPDATE/DELETE), и
остаток на любой момент точно восстанавливается функцией `stock_at` — последнее движение
каждого зеркала до момента даёт его статус и площадку. Для прошедшей даты «Отгрузка» берёт
остатки на конец того дня, отгрузки — закрытые каналы того дня, задачи — задачи на ту дату.
Пояснительные надписи на странице убраны; вместо «Данные на …» — «Сегодня, данные на …» или
«Итог дня ДД.ММ.ГГГГ: остатки на конец дня».

## 2026-10-21 (4) — «склад + задачи − отгрузка» без двойного счёта; убраны «Учит. + задачи» и «общее»

Задачи в «склад + задачи − отгрузка» прибавляются сразу, как только поставлены, но только
несделанная часть: план − этикетки задач, уже принятые сканом до конца дня. Иначе готовое
зеркало считалось бы дважды — оно уже в остатке «до отгрузок». Столбцы «Учительская + задачи» и
«общее» убраны по просьбе владельца (с экрана и из XLSX).

## 2026-10-21 (5) — Склад общий

Владелец: «склад общий, на какой площадке задачи — не имеет разницы». «склад − отгрузка» и
«склад + задачи − отгрузка» считаются по сумме площадок (Коминтерна + Учительская), задачи —
обеих площадок (несделанная часть), отгрузки в колонках каналов — со всех площадок.

## 2026-10-21 (7) — Ввод остатков, открытые каналы, «Сканер / Камера»

- **Ввод остатков** (`/stock-entry`, кладовщик своей площадки и админ): печать с запасом —
  зеркала сразу на склад от служебного «Инвентаризация» (миграция 0009), без скана (на складе
  нет интернета). Лишние этикетки сканируются там, где есть связь: IN_STOCK → «Списано»
  движением `inventory_fix` (не брак). Убрать можно только этикетку ввода остатков. Убрать
  «N из M без скана» нельзя намеренно: неизвестно, какие номера не наклеены.
- **Открытые каналы:** красная плашка на «Отгрузке» и предупреждение на табло; в 23:59

  считается в «Озон 1», это видно в плашке за тот день).

  держит фокус, экранная клавиатура не выскакивает, кнопка камеры становится основной.
