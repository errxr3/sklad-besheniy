# CLAUDE.md — правила работы над проектом «Склад зеркал»

Этот файл читается автоматически в начале каждой сессии. Соблюдай его строго.

## Что строим

Веб-система складского учёта зеркал. **Полная спецификация — `SPEC.md`.** Читай её целиком в начале каждой сессии перед работой; номера разделов ниже — оттуда.
Входные данные: `docs/input/` (TOP.xlsx, образец этикетки, скриншоты гугл-таблицы). Эти файлы не изменять.

## Режим работы: автономно, без вопросов

- Владелец не сидит рядом. **Не задавай вопросов и не жди подтверждений.** Неясное решай сам разумно и записывай в `DECISIONS.md` (дата, вопрос, решение, почему).
- Работай этап за этапом до конца списка. Закончил этап — сразу начинай следующий в этой же сессии.
- Если что-то невозможно сделать в этой среде (нет доступа к Google, нет телефона для камеры) — сделай код и тесты с подменой (mock), запиши в `PROGRESS.md` в раздел «Проверить руками» и иди дальше.

## Память между сессиями: PROGRESS.md

Сессия может оборваться в любой момент (кончился лимит, закрыли окно). Поэтому:

1. **В начале каждой сессии:** прочитай `PROGRESS.md`, `DECISIONS.md`, `git log --oneline -20`, `git status`. Если есть незакоммиченные изменения — разберись, доведи до рабочего состояния или откати (`git stash`), и только потом продолжай.
2. **Продолжай с первого незакрытого пункта** в `PROGRESS.md`. Не переделывай то, что уже отмечено `[x]` и закоммичено.
3. **Обновляй `PROGRESS.md` после каждого законченного шага**, а не в конце этапа: отметь `[x]`, допиши, что дальше и что важно знать следующей сессии (≤ 5 строк).

Формат `PROGRESS.md`:
```
# Прогресс
Текущий этап: N — название
Следующий шаг: ...

## Этапы
- [x] 0. Каркас
- [ ] 1. ...

## Заметки для следующей сессии
- ...

## Проверить руками (владельцу)
- ...
```

## Git

- Репозиторий инициализирован в корне. Ветка `main`.
- **Коммит после каждого законченного шага**, когда тесты зелёные. Маленькие коммиты лучше одного большого.
- Сообщения коммитов на русском: `этап 2: печать этикеток PDF + тесты`.
- **В конце каждого этапа:** все тесты зелёные, `ruff check .` и `mypy app` без ошибок, обновлён `PROGRESS.md`, коммит, затем тег `stage-N` (`git tag stage-2`).
- Если настроен `origin` (`git remote -v` показывает адрес) — после каждого этапа `git push origin main --tags`. Если push не прошёл — запиши в PROGRESS.md и продолжай, не останавливайся.
- Никогда: `git push --force`, переписывание истории, коммит `.env` и секретов, коммит сломанного кода в конце этапа.

## Качество — не переходи к следующему этапу, пока не выполнено

- Все тесты этапа и всех прошлых этапов проходят: `docker compose run --rm app pytest -q` (или локально `pytest -q` с тестовой PostgreSQL).
- Нет `TODO`, `FIXME`, `NotImplementedError`, `pass` вместо логики в уже сделанных частях.
- Если тест падает — чини причину, а не тест. Тест можно менять, только если он противоречит SPEC.md; тогда объясни в DECISIONS.md.
- Не больше 3 попыток подряд починить одну и ту же ошибку одним способом: если не выходит — смени подход, упрости, запиши в DECISIONS.md.

## Этапы

Каждый этап = рабочее состояние + тесты + коммит + тег.

### Этап 0 — Каркас
- Структура проекта, `pyproject.toml`, FastAPI-приложение, `/health`.
- `docker-compose.yml` (app, postgres, caddy), `Dockerfile`, `.env.example`, `.gitignore`.
- SQLAlchemy + Alembic, первая миграция со **всеми** таблицами из SPEC §8 (индексы, ограничения, частичные уникальные индексы, триггер запрета UPDATE/DELETE на `movements`, sequence номеров).
- pytest с отдельной тестовой БД PostgreSQL, ruff, mypy.
- Готово, когда: `docker compose up -d` поднимается, `/health` = 200, миграции применяются, тест на триггер `movements` и тест sequence зелёные.

### Этап 1 — Справочник, сотрудники, вход, роли
- Импорт TOP.xlsx (SPEC §9) — CLI и страница; нормализация артикулов; префиксы Z/A/AT/X; подгруппы; цвета строк; `sort_order`.
- Площадки Коминтерна и Учительская (миграцией), служебный сборщик «Остаток на запуск».
- Сотрудники 4 ролей, PIN argon2, блокировка после 5 ошибок, сессии, CSRF, `create-admin`.
- Проверка ролей на сервере + таблица «маршрут → роли» и параметризованный тест.
- Базовый шаблон страниц (мобильный, крупный шрифт), меню по ролям, главные страницы ролей (SPEC §4).
- Готово, когда: тесты §12 п. 8, 9, 10, 14, 17 зелёные.

### Этап 2 — Зеркала: статусы, печать, приёмка
- Модуль переходов (единственный словарь, функция `apply_transition`, `FOR UPDATE`), движения.
- «Сделал зеркало»: выбор артикула, печать PDF этикеток (SPEC §7), скан приёмки, перепечатка.
- Общий JS-компонент скана: поле в фокусе, зелёный/красный экран, звук, последние 10 сканов, «Нет связи, скан НЕ записан», камера (библиотека в `static/vendor/`).
- Карточка зеркала, список «Напечатано старше суток».
- `verify-stock`.
- Готово, когда: тесты §12 п. 1, 2, 3, 4, 5, 15, 16, 18 зелёные.

### Этап 3 — Смены по QR и задачи
- Код смены площадки, PDF A4 с QR, перевыпуск, начало/конец смены только камерой, геопроверка (выкл. по умолчанию), автозакрытие в 00:05 (SPEC §5).
- Запрет сканирования без смены для сборщика и грузчика.
- Табло «Кто на смене», табель + CSV.
- Задачи: постановка на завтра, «Мой день» с автоподсчётом прогресса, копирование невыполненного, журнал задач, отчёт план/факт (SPEC §6.1–6.2).
- Готово, когда: тесты §12 п. 11, 12, 13 зелёные.

### Этап 4 — Отгрузка и складские операции
- Погрузка на паллету для грузчика (SPEC §6.4), второй скан ШК маркетплейса, отмена отгрузки.
- Перемещение и приёмка между площадками, инвентаризация, списание, возвраты (SPEC §6.5–6.7).
- Журнал с фильтрами + CSV, отчёт «Выработка».
- Готово, когда: тесты §12 п. 6 зелёные, плюс тесты на каждый сценарий.

### Этап 5 — Остатки как в гугл-таблице и выгрузка
- Экран «Остатки» точно по SPEC §6.9 (порядок строк из TOP, заголовки подгрупп, цвета, столбцы площадок и задач, копирование TSV, XLSX). Сверься со скриншотами `docs/input/gsheet_*.png`.
- Выгрузка в Google Sheets раз в 5 минут + «Выгрузить сейчас» (SPEC §10); без ключа — пропуск с сообщением.
- Готово, когда: тесты §12 п. 19, 20 зелёные.

### Этап 6 — Интеграция, отчёты, сдача
- API для BLAGO OTGRUZKI с ключами, сверка с заказом при отгрузке (тест §12 п. 7).
- Страница «Состояние», бэкапы `pg_dump` с хранением 30 дней.
- Сквозной тест Playwright (SPEC §12, последний абзац).
- `README.md`, `docs/инструкция.md`, итоговый `DECISIONS.md`.
- Пройти чек-лист SPEC §13 и записать результат в `PROGRESS.md` (что проверено автоматически, что — «проверить руками»).
- Финальный коммит, тег `v1.0`, push.

## Когда всё готово

Напиши в `PROGRESS.md` раздел «Итог»: как запустить, что проверено, что владелец должен проверить руками (печать на реальном термопринтере, камера на телефоне, доступ к Google), и выведи то же самое в ответ.
